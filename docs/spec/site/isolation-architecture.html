APMU isolation architecture

The APMU sees events from every core and can act on the system. This design makes the kernel module the only party that turns that power into concrete hardware configuration, so a hostile application cannot use the APMU to read what it should not, disturb other applications, or reconfigure the SoC.

Proposal, 2026-10-07. Decided: counters belong to the kernel (section 4); components are eBPF programs checked by the kernel's own BPF verifier (section 7). Neither is implemented yet. Facts about the hardware are from the RTL (he-soc es/quad-evu-standalone/OpenDRAM) and the current module. What a component's own code may do is out of scope here and handled by separate verification work; this design fixes the interface that work plugs into.

1. What the APMU can do today

Every capability below is reachable either by a host process that can write APMU registers, or by code running on the PE. Today the module is the only intended host writer, but nothing in the hardware stops PE code from doing any of it.

2. Threat model and goals

Trusted: the Linux kernel and the apmu module, the apmu-os base image (loaded by the kernel), the hardware, and the administrator who sets policy.

Untrusted: every userspace process, whatever its uid, including several colluding processes and processes that fork, pass file descriptors, crash mid-call, or issue arbitrary ioctls with crafted arguments and objects.

Out of scope (separate work): whether a component's code does only what its manifest says. This design rejects code that touches resources it was not granted, using the kernel's BPF verifier plus APMU-specific checks, and states exactly what they must enforce (section 7). What a component does within its grants is left to that separate work.

G1

Confidentiality

An application learns only events and data it is entitled to: its own cores, or the whole system if it holds the privilege for that.

G2

Integrity

No application can alter another's components, counters, messages or results.

G3

Fair availability

No application can exhaust slots, memory, counters, queue space or PE time for everyone else.

G4

System safety

No unprivileged application can use the APMU to change SoC configuration, interrupt routing or core behaviour.

3. Architecture

Four zones, two boundaries that matter. Userspace talks only to /dev/apmu and only in abstract terms. The kernel module is the reference monitor: it decides, binds abstract requests to concrete hardware, and is the only writer of APMU configuration. The base image on the PE executes what the kernel installed and stamps every message with where it came from.

Rules that hold everything together

  1. Nobody but the kernel names a raw resource. Userspace never passes a counter number, register address, physical address or component id that the kernel acts on directly. It asks for an event in semantic terms and gets an opaque handle back.
  2. The kernel is the only writer of APMU configuration. It programs event selectors, budgets, the IOPMP and IRQ routing itself, after checking policy. Components get the result (which counters are theirs), never the means.
  3. Every object is owned by one session (an open file), every operation is checked against that ownership, and sharing happens only through an explicit grant.
  4. Every hand-over is scrubbed. Counters are reset and their selectors cleared, DSPM and ISPM ranges zeroed, mailboxes and in-flight replies dropped, before a resource changes owner.
  5. Everything is bounded per user: slots, memory, counters, in-flight requests, message rate, and PE time.

5. Event visibility policy

The APMU attributes every event to a core (the EVU port, the LLC port and the DRAM source all identify the core). Linux schedules processes on cores, not cores on processes, so "my own events" only means something when the cores are reserved. The policy follows Linux's existing rule for perf (perf_event_paranoid, CAP_PERFMON): watching activity that is not yours requires a privilege.

Scope requestedGranted whenKernel translation
ownThe caller's cgroup holds an exclusive core lease from the administrator (an exclusive cpuset), and the caller is confined to itPort and source masks restricted to the leased cores; if the lease set cannot be expressed as one mask, several counters or a refusal
core:nCore n is in the caller's lease, or the caller has CAP_PERFMONSingle core selected
system (any source)CAP_PERFMON (or CAP_SYS_ADMIN)Wildcard masks

Leases are revocable: when the administrator changes the cpuset, the kernel stops the affected counters before the cores are shared again, and the session sees its handle report revoked. With the board's current single-hart Linux, only system scope is meaningful, so the first implementation can be "CAP_PERFMON or nothing", with leases added once more cores run Linux or partitioned workloads.

6. The interface

any user Session API

  • open("/dev/apmu"): a session; the kernel records uid, capabilities and cgroup now, like perf does.
  • INSTALL {eBPF program, manifest} → handle. Fails with a reason: quota, scope, no space, rejected by verifier.
  • UNINSTALL {handle}
  • SEND {handle, ≤64 words}, RECV {handle, timeout}, poll() for replies and overflow notifications.
  • mmap(handle): the component's shared buffer, if the manifest asked for one.
  • INFO: the session's own handles and their state; for everyone else only totals (free slots, free bytes), no owners or placements.
  • GRANT {handle, uid | gid} (optional): lets another user send to a component; replies still go only to the sender.

administrator Control API

  • Policy (sysfs or configfs): quotas per user and group, event classes allowed per group, core leases, whether regulation is enabled.
  • System components: persistent, not owned by any session, with an explicit access list.
  • Regulation: MemGuard budgets and period, overflow-to-core actions, EVU event export.
  • Reload the base image, evict or kill any component, read the full ledger.
  • Debug mode (raw access for apmuctl): off unless the module is loaded with it, and logged.

Manifest: what an install asks for

The manifest travels next to the object. The kernel grants exactly what it lists or refuses, then writes the bindings into the component (it already links the object, so it patches the values in).

manifest {
  counters[] = {                          // at most the user's counter quota
    { class: dram, event: rd_res, op: max(info[15:0]), scope: own },
    { class: llc,  event: rd_req, op: count,           scope: core:1 },
  }
  notify_overflow = [1]                   // counter 1 overflows reach this session
  shared_buffer   = 4096                  // bytes, rw, mapped with mmap(handle)
  pe_budget_us    = 50                    // longest handler run the component asks for
}
// bound by the kernel, patched into the object at link time:
component_counters[] = { 7, 12 }          // indices chosen by the kernel
component_bitmask    = (1u << 7)          // wake-up mask, computed by the kernel
component_window     = { 0x8f3a0000, 4096 }

Each check happens before anything reaches the hardware; the hardware is touched only in the last third, using ranges not owned by a running component.

Decided 2026-10-07: components are eBPF, checked by the Linux kernel's own verifier. Applications submit eBPF bytecode (restricted C compiled with clang -target bpf) instead of RV32 objects. A patched kernel adds a program type, BPF_PROG_TYPE_APMU; the unmodified verifier checks it, and apmu.ko translates it to RV32 for the PE through the BPF offload hooks, the path NFP SmartNIC offload already uses. Kernel changes, kept small

  • Program type. An entry in bpf_types.h and verifier ops: is_valid_access describes the context (event info) and the window as a fixed-size region; get_func_proto lists the helpers (reply, printf, counter_read, counter_reset). The verifier's own logic is not modified, so the claim "checked by the kernel verifier" can be confirmed from a short diff.
  • Offload ops in apmu.ko (bpf_prog_offload_ops). insn_hook rejects instructions the PE cannot run; finalize runs the APMU-specific checks (worst-case path length against pe_budget_us, counter slots against the grants); translate emits RV32. Checks the kernel verifier does not make are kept in these callbacks so it is clear which part proves what.
  • Host-only passes off for this type: Spectre hardening, ALU sanitation and constant blinding protect nothing on the PE and cost ISPM space.
  • Unprivileged load for this type, gated by the manifest policy rather than CAP_BPF. Most past verifier bugs led to host compromise because the program ran on the host; an APMU program runs on the PE, behind the translator's masks.
  • Maps, if components need them, are device-bound and live in DSPM; the shared buffer (mmap(handle)) stays as it is.

Translator

Based on the kernel's eBPF to RV32 JIT (arch/riscv/net/bpf_jit_comp32.c, built only for 32-bit kernels, so ported into apmu.ko). eBPF registers are 64-bit, so code is larger and slower than hand-written RV32; programs compiled for 32-bit ALU operations and the verifier's zero-extension elimination reduce it. The translator masks every load and store into the component's regions even though the verifier has proved them in range: isolation then does not depend on the verifier being bug-free, at one or two instructions per access.

Not covered statically: a handler that overruns its budget anyway (a slow helper, a bad worst-case estimate). Stopping it needs the PE timer interrupt (section 9); until then the module's ping timeout and recovery are the backstop, which restarts every component. If PMP becomes available on the PE, rows 1 to 3 and 5 also gain a hardware check.

8. Keeping applications apart

Messages

  • Handles are per session and carry a generation number, so a stale handle can never reach a component that later took the same slot.
  • The kernel tags each request with its session; the base stamps every reply with the component it dispatched to and that tag. A component cannot claim to be another one, and a shared component's replies go back to whoever asked.
  • Replies still in the queue when a component is removed are dropped, not delivered to the slot's next owner.
  • Admission control: a cap on in-flight requests per session and round-robin between sessions, so one sender cannot fill the 760-byte queue.

State and resources

  • On uninstall, recovery or revocation: counters reset and selectors cleared, ISPM/DSPM ranges zeroed, IOPMP entry removed, notifications cancelled.
  • Quotas per user: slots, ISPM/DSPM bytes, counters, shared-buffer bytes, in-flight requests, messages per second.
  • INFO shows a session only its own components; other users' presence, placement and counters are not visible.
  • Closing a session (or process exit) removes everything it owns.

PE time and recovery

  • The base writes the id of the component it is about to run into DSPM. When the PE stops answering or traps, the supervisor knows whom to blame (trap address, or the running component).
  • A component that causes repeated recoveries is evicted and its owner told why; repeat offenders lose install rights for a while.
  • Recovery restarts every component, so its cost falls on everyone: eviction keeps one application from doing that repeatedly.

Host-side hardening

  • The module claims the APMU MMIO range (request_mem_region) and the kernel is built with CONFIG_IO_STRICT_DEVMEM: even root cannot map the APMU through /dev/mem while the module owns it.
  • The base image comes from /lib/firmware (optionally signed), not from an ioctl.
  • /dev/apmu is mode 0660, group apmu, not 0666.
  • Every ioctl copies its arguments once and validates them; no pointer from userspace ever reaches the PE.

9. What software alone cannot enforce

The PE has no privilege levels (Ibex is built with PMPEnable = 0), the counter instructions take any index, and its data port reaches the APMU registers. Until the hardware changes, isolation between components on the PE rests on the verifier. These RTL changes would move it into hardware, in order of value:

  1. PMP and user mode on the PE. Components run in U-mode with PMP regions set by the base from the kernel's grants: their code, data, stack and window only; no APMU registers.
  2. A per-context counter mask. A register, writable only in M-mode, that limits which indices cnt.* may touch.
  3. The IOPMP on the APMU master path in every bitstream (APMU_IOPMP), programmed by the kernel.
  4. A timer interrupt on the PE (all PE interrupts are tied off in pmu_core.sv) so the base can preempt a handler that exceeds its budget.
  5. The DSPM arbitration fix (apmu.md §14.18). Today a host write on behalf of one application can corrupt another component's data, which breaks G2 between applications.
Remaining risks with all of the above. Components share one PE, so an application can still infer other components' activity from the latency of its own replies (timing side channel); the in-flight caps and time budgets limit but do not remove it. Core-granular events also leak the activity of anything else scheduled on a leased core, which is why leases must be exclusive.
